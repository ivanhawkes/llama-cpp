# llama-cpp flake

Dev shell + one-command GPU inference server for llama.cpp (Qwen3 27B on an RTX 5060 Ti).
This is **not** a NixOS system configuration — the flake exposes only `devShells`.

## Quick start

```sh
nix develop        # or just cd here with direnv; .envrc runs `use flake . --impure`
run-server         # starts llama-server on 0.0.0.0:8080 (Qwen3.8-27B IQ3_S, all layers on GPU)
smoke-test         # starts run-server, polls /health up to 300s, then kills it; exit 0 = healthy
```

`smoke-test` honors `SMOKE_TEST_PORT` (default 8080) and `SMOKE_TEST_TIMEOUT` (default 300 s).
Server log during the test: `/tmp/llama-smoke-test.log`.

`run-server` tees all server output to `/tmp/llama-server.log` (truncated per start, override
with `LLAMA_SERVER_LOG`) while echoing to the terminal, and serves Prometheus metrics at
`http://localhost:8080/metrics`. Per-session performance summaries are appended to `perf-log.md`.

## GPU facts (source of truth: nvidia-smi, *not* hardware.json)

```sh
nvidia-smi --query-gpu=index,name,memory.total --format=csv,noheader
# 0, NVIDIA GeForce RTX 5060 Ti, 16311 MiB   <- run-server's preflight requires index 0 to be this card
# 1, NVIDIA GeForce RTX 4060, 8188 MiB       <- the ~15GB model does NOT fit here
```

fastfetch's GPU list order is arbitrary — never use `hardware.json` to decide CUDA indices.
If the index mapping ever changes, `run-server` fails fast with a clear message (preflight guard).

Observed live (2026-10-03): one running `llama-server` process holds ~10GB on idx0 **and**
~5.6GB on idx1 — this build splits the MTP draft across both GPUs (see the NOTE in
`flake.nix`). So VRAM contention on *either* card can break startup, even though the
preflight only checks free VRAM on idx0.

## Model & cache

- Model: `ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF:IQ3_S` (~15GB), pulled from Hugging Face on first start.
- Cache: `.hf-cache/` in the repo root (gitignored). `HF_HOME` is exported by the devShell
  shellHook as `$PWD/.hf-cache` (expanded at shell start — a flake-level `env` value would stay
  literal, since Nix does not expand `$PWD`).

## hardware.json field definitions

Generated by `fastfetch --format json > hardware.json`. Do not hand-edit; regenerate when stale
(e.g. `find hardware.json -mtime +7`). Fields this repo's decisions rely on:

- `GPU[].name`, `GPU[].driver` — GPU model and driver (informational only; index mapping comes from nvidia-smi)
- `CPU.march`, `CPU.cores` — microarchitecture and core counts
- `Memory.total` — total RAM in bytes
- `Disk[].mountpoint`, `Disk[].bytes` — mount points and sizes in bytes

## Known pitfalls

- Picking the wrong GPU index loads a ~15GB model onto the 8GB card → OOM/crash. The preflight
  guard in `run-server` catches this before startup.
- First `run-server` start downloads the model; expect a long pause before `/health` responds
  (smoke-test timeout is 300 s by default).
- Nix `''` strings interpolate `${...}` — shell scripts embedded in `flake.nix` must avoid brace
  expansion (see the comment in the flake).

## Reproducing a startup failure

If `smoke-test` (or a manual `run-server`) never reaches `/health`:

1. Read `/tmp/llama-smoke-test.log` — it contains the full `run-server` output, including
   the preflight GPU check and the model-load error.
2. Check contention before blaming the flake:
   - **Port** — `curl -s localhost:8080/health`: if something already answers, a second
     server cannot bind 8080 (use `SMOKE_TEST_PORT=<other>` for smoke-test; it now sets both
     the bind port and the polled URL).
   - **VRAM** — `nvidia-smi --query-gpu=index,memory.used,memory.free --format=csv,noheader`:
     the ~15GB model needs index 0 mostly free; a running server holds it and a second load
     will OOM. There is no way around this from inside a session served by that server.
3. Anything failing *after* the preflight line is a model-load/VRAM problem, not an
   index-mapping problem (the guard already ruled the latter out).
